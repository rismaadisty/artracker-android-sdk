Perbandingan per aspek

SekarangRefactor (mode saat error)
Siapa yang merekam fakta Sesi yang lolos sampleRate (default 0.1 = 10%), diputuskan per session id dengan hash FNV-1a yang sama dengan web SDK. Default enabled = false. usulan Sesi yang lolos onErrorSampleRate (usulan default 1.0 = semua). Lebih banyak HP yang menjalankan capture.
Apa yang diupload fakta Seluruh sesi. Chunk ditutup tiap 10 dtk (maks 2 MB gzip), masuk antrean SQLite, lalu dikirim. usulan Hanya ~60 dtk terakhir sebelum pemicu. Sesi tanpa pemicu: 0 byte.
Kuota per sesi terekam fakta Budget ±5 MB/menit. Terukur 16,91 MB untuk 5 mnt scroll terus (2 fps, STANDARD), ±3,4 MB/menit. ±1–5 MB per pemicu, nol bila tidak ada pemicu.
CPU di main thread fakta Capture p95 6,2 ms per frame (target 16 ms), OPPO CPH2387, debug build. Sama per frame. Usulan: 1 fps, bisa diturunkan ke 0,5 fps atau kualitas LOW di mode ini.
Baterai fakta Belum diukur. Background CPU < 0,1% (replay berhenti saat app di background). Per HP sama atau sedikit lebih kecil (tanpa upload). Tetap perlu diukur.
Penyimpanan di HP fakta Antrean replay maks 50 MB (ReplayStore), dikosongkan setelah upload. usulan Buffer bergulir maks 13 chunk × 5 dtk (60 dtk) ≈ maks 5 MB; chunk lama ditimpa.
Crash yang punya replay ±10% (hanya crash di sesi terpilih). Hampir semua. Risiko: ≤10 dtk terakhir yang belum ditulis ke disk bisa hilang saat proses mati.
ANR fakta Dideteksi watchdog (API 24–29, saat itu juga) dan ApplicationExitInfo (API 30+, baru terbaca saat app dibuka lagi). API 24–29: upload langsung. API 30+: buffer dari disk dikirim saat app dibuka lagi.
Error yang di-log fakta Hanya menandai chunk has_error. Flag ini belum dipakai di backend/dashboard. usulan Memicu upload buffer + rekaman lanjut sebentar. Dibatasi per sesi supaya error beruntun tidak boros kuota.
Privasi Masking di HP sebelum JPEG dibuat. Masking sama. Data yang keluar dari HP jauh lebih sedikit.
Sisi web/backend Replay dimulai dari awal sesi. terbuka Replay dimulai di tengah sesi (frame pertama harus full snapshot). Dashboard perlu label "replay sebelum crash" dan tautan ke crash-nya.
Kompleksitas SDK Sudah jalan dan teruji. Baru: buffer bergulir di disk, status "ditahan" vs "siap kirim", pengiriman saat launch berikutnya, batas per sesi.

Alur di HP

Sekarang

  1. Sesi mulai, cek sampleRate.
  2. Terpilih: capture → masking → JPEG → chunk 10 dtk.
  3. Chunk ditutup → antrean SQLite → upload.
  4. Error di-log: chunk diberi flag has_error.
  5. Ulangi sampai sesi selesai / app ke background.

Refactor

  1. Sesi mulai, cek onErrorSampleRate.
  2. Terpilih: capture → masking → JPEG → chunk 10 dtk (sama).
  3. Chunk ditutup → disimpan dengan status ditahan; hanya 60 dtk terakhir (maks 13 chunk) yang disimpan.
  4. Pemicu: chunk ditahan sesi itu diubah jadi siap kirim → upload.
  5. Sesi berakhir tanpa pemicu: chunk ditahan dihapus.

Yang perlu diputuskan

  1. Mode lama tetap ada? Usulan: tetap bisa dipakai (misalnya sampleRate = 0.01 untuk melihat perilaku normal), tapi default-nya 0 dan mode saat error jadi default.
  2. Panjang buffer. Usulan 60 dtk. Lebih panjang = konteks lebih banyak, kuota per pemicu naik.
  3. Batas upload error di-log per sesi. Usulan maks 1–3 kali, dengan jeda antar pemicu.
  4. fps dan kualitas di mode ini. Usulan tetap 1 fps STANDARD; turunkan bila pengukuran baterai buruk.
  5. Hanya Wi-Fi? Opsi: upload replay ditunda sampai Wi-Fi. Paling hemat kuota, tapi replay datang terlambat.
  6. Web SDK dan iOS. Sampling sekarang identik lintas platform. Perlu disepakati apakah mode ini juga dibawa ke web/iOS.
  7. Dashboard. Menampilkan replay yang dimulai di tengah sesi dan menautkannya ke crash/error.
